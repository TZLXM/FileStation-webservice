# v1.6 修正设计交叉审查结果

## 总体结论

启动顺序与 NestJS 生命周期**可行**（migrations 在 `NestFactory.create()` 内 TypeORM `onModuleInit` 触发、`OnApplicationBootstrap` 在 `app.init()` 触发、`ensureInitToken` 在 listen 前调用时无任何请求存在，纯 DB 写不阻塞）；统一 access 端点与全局约束（单端点 `{password?}`、page+none/password）一致；DTO 装饰器与 `whitelist+transform+forbidNonWhitelisted` 的组合本身正确（`enableImplicitConversion:false` 下 `@Type(()=>Number)` 已补齐）。但有 **1 个确认的模块循环**、若干编译/运行级漏洞必须修正。

---

## P0：会导致编译失败或运行即错

**1. AuthModule ↔ SettingsModule 确认循环，设计未落定方案（§4.5）**
AuthService 注入 SettingsService → AuthModule imports SettingsModule；而 SettingsController 用 JwtAuthGuard → SettingsModule imports AuthModule。**这是确定的直接循环，不是"若构成"**，Nest 启动即抛 `UndefinedDependencyException`。FilesModule→SettingsModule 亦被波及。
修正：二选一并写死——
- (a) 推荐：抽 `SecurityModule`（JwtModule 注册 + JwtStrategy + JwtAuthGuard），AuthModule 与 SettingsModule 都 import 它；SettingsModule **不再** import AuthModule。之后依赖链单向：FilesModule→SettingsModule、FilesModule→SecurityModule、AuthModule→SettingsModule+SecurityModule，无环。
- (b) 双侧 `forwardRef(() => ...)`（可工作但脆弱）。
同时必须显式写明：`SettingsModule` 需 `exports: [SettingsService]`（供 FilesModule/AuthModule 注入）。

**2. 设置合并 spread 在 `useDefineForClassFields=true` 下会清空未提交字段（§4.3）**
`{ ...current, ...body.site }`：若 tsconfig target 为 ES2022（`useDefineForClassFields` 默认 true），DTO 类声明的字段会成为值为 `undefined` 的自有属性，spread 后用 undefined 覆盖 current 的已有值 → 管理员只改 site.name 会清空 icon/theme_color。
修正：不依赖 tsconfig 行为，统一加 `omitUndefined` 辅助函数后再 merge：
```typescript
const clean = <T extends object>(o: T) =>
  Object.fromEntries(Object.entries(o).filter(([, v]) => v !== undefined)) as Partial<T>;
await this.settingsService.set('site', { ...current, ...clean(body.site) }, userId);
```

**3. `accessShare` 读不到 passwordHash 的风险（§2.1）**
若 Share 实体 `password_hash` 列为 `select: false`（密码哈希常规做法），`findOne({ where: { id } })` 返回的 `share.passwordHash` 恒为 undefined → 所有密码分享永远报 `INVALID_SHARE`。
修正：用 QueryBuilder 显式取回：`.addSelect('share.passwordHash')`，或在 `getShareInfo` 内部一次取齐（顺带消除第二次 findOne）。

**4. `FileStatus.DELETED` 需要过 DB CHECK 约束（§4.4）**
v1.5 迁移若对 `files.status` 有 `CHECK (status IN (...))` 且不含 `'deleted'`，`UPDATE ... SET status='deleted'` 直接 `SQLITE_CONSTRAINT`。SQLite 改 CHECK 必须重建表。
修正：把 `deleted_at INTEGER` 列与 status CHECK 含 `'deleted'` 放进**同一个重建表迁移**（12 步表重建模式），不要拆两个迁移。此条必须写进迁移修正域的任务，且 §4.4 标注为硬依赖。

**5. `@Cron` 静默不生效（§4.4）**
设计未提及 `@nestjs/schedule`。若 AppModule 未注册 `ScheduleModule.forRoot()`，`processLifecycle` **永运行且无报错**——"无人清理"问题依旧。
修正：AppModule 显式 `imports: [ScheduleModule.forRoot()]`，package.json 加 `@nestjs/schedule`。

**6. GET→PUT 设置回环会 400（§4.3 + StorageSettingsDto）**
GET /settings 返回 `storage.path` 与 `security.totp_required:false`；管理端常见的"取回-修改-整体 PUT"模式会因 `path` 触发 forbidNonWhitelisted 400。
修正：二选一并写进前端任务——(a) SettingsPage PUT 前显式剔除 `path`（推荐，保持后端严格）；同时在 deploy/API 文档中注明 path 为只读字段。`totp_required:false` 回传可被 `@IsIn([false])` 接受，无碍。

**7. DTO 落盘路径与模块位置不一致（§1）**
v1.5 事实：UploadsController/UploadsService 在 `src/files/`。`init-upload.dto.ts`/`complete-upload.dto.ts` 路径应为 `apps/server/src/files/dto/`，不是 `apps/server/src/uploads/dto/`。

## P1：逻辑缺陷

**8. 登录计时拉平代码不可读且有副作用（§4.5）**
`(await import('bcrypt')..., false)` 逗号表达式依赖求值顺序、每次失败动态 import。
修正：模块级常量 `const DUMMY_HASH = '$2b$10$....（预生成）'`，用户不存在时 `await bcrypt.compare(password, DUMMY_HASH)` 后统一走失败路径。

**9. 全局锁定计数 → 登录 DoS（§4.5）**
单 key 全局锁定意味着任何人持续投递错误密码可让管理员**永远**无法登录（每次解锁窗口立即被打满重锁）。
修正：至少文档化为已知限制并加缓解：锁定期间失败不再延长但**解锁后计数从 max-1 起步**（再错 1 次即重锁且 `locked_until *= 2` 指数退避，上限 24h）；或按 username 分 key（Phase 1 单管理员，二选一即可，但需写明决策）。

**10. `logout(refreshToken)` 签名变更未给实现（§2.4）**
v1.5 logout 大概率按 user.id 吊销。新签名要求 AuthService 按 token 哈希定位并吊销，且对未知/已过期 token **幂等成功**。
修正：补实现 `logout(refreshToken)`：`hashToken → refresh_tokens 条件 UPDATE revoked=1 WHERE token_hash=? AND revoked=0`，不抛异常。

**11. api.ts Authorization 大小写（§2.3）**
调用方若传 `authorization`（小写），检查漏判后产生双头，fetch/Headers 合并为 `Bearer a, Bearer b` → 后端解析失败。
修正：`const hasAuth = Object.keys(requestHeaders).some(k => k.toLowerCase() === 'authorization')`，或改用 `new Headers(init)` API set。

**12. `FileLifecycleService` 对 ENOENT 会死循环重试（§4.4）**
磁盘删失败 `continue` 保留下轮重试；若文件本就不在磁盘（手动删过），`deleteFile` 抛 ENOENT → 永远重试 + 日志刷屏。
修正：`StorageService.deleteFile` 对 ENOENT 视为成功（catch code==='ENOENT' return）。

**13. PATCH `expires_at` 无条件复活文件（§2.6）**
`updateData.status = FileStatus.ACTIVE` 会把 DELETING/DELETED 文件改回 active。
修正：`FilesService.update` 前置条件 `WHERE id=? AND status IN ('active','expired')`（条件 UPDATE 抢占），不满足抛 404/409；Controller 侧只组 payload。

**14. `default_expire_hours` 旧值兼容（§4.2）**
DTO `@Min(0)` 禁负，但库中可能已存 -1（旧"永久"语义），GET 后回 PUT 直接 400。
修正：`getStorageSettings` 读出时归一 `Math.max(0, stored.default_expire_hours)`。

**15. Query 参数 DTO 缺失（第 3 审查点的缺口）**
本设计只覆盖 @Body。文件列表/文件夹子项/审计日志/传输事件等 GET 端点的 `page/page_size/folder_id` 仍无校验（interface 或裸 `@Query()` 不受 whitelist 约束）。
修正：补 `ListFilesQueryDto` 等，分页参数一律 `@Type(()=>Number) @IsInt() @Min(1)` + `@Max(200)`；与 Body DTO 同一套 Pipe 即生效。

**16. access 端点暴力破解无防护（§2.1）**
登录有锁定，分享密码没有任何限流，64 位空间外的弱密码（4 位起）可在线穷举。
修正：最低限度——密码错误时同样计入 §4.5 的锁定计数（或独立 `share_access_lockout` key，按 shareId 计），连续 5 错锁 10 分钟。

**17. `ShareAccessDto` 空 body 细节（§2.1）**
免密分享前端必须 POST `{}` 且带 `Content-Type: application/json`，否则部分路径下 body 为 undefined 导致 `body.password` 抛 TypeError。
修正：Controller 写 `@Body() body?: ShareAccessDto` 并 `body?.password`，前端统一发 `{}`（双保险）。

**18. 次要项**
- `verifyStartedAt`（§3.1）是 UploadSession 新列 → 归入迁移域，与 verifying 超时任务同迁移。
- `app.listen(port, '127.0.0.1')`：Win11 上 `localhost` 优先解析 ::1，dev 文档必须写死访问 `http://127.0.0.1:8080`（Nginx 反代无影响）。
- `main.ts` 阶段 1 直接读 `process.env.FILESTATION_*`，StorageService 读 `ConfigService.get('app.storagePath')`——必须确认 configuration.ts 的映射源是**同一组环境变量**，否则两阶段目录可能分叉。
- `StorageSettingsDto` 缺 `@Max` 上限校验的 `default_expire_hours` 已有 87600，OK；但 `CreateShareDto.expires_at` 允许过去时间——service 层需拒绝（v1.5 是否已有校验需确认）。
- `@Param('id')` 建议统一加 `ParseUUIDPipe`，非法 id 早 400 而非打穿到 DB。

## 对 5 个审查点的直接回答

1. **统一 access**：与约束一致；需同步删前端 `/verify` 分支与相关 E2E；补 §16 限流。
2. **启动顺序**：可行。migrations 于 `create()`、Bootstrap 钩子于 `init()`、token 于 listen 前（无请求可阻塞）。唯一前置：解决问题 1 的循环，否则 create() 即失败。
3. **DTO×Pipe**：Body DTO 全部兼容（`@Type` 已配）；缺口在 Query DTO（问题 15）与 spread 合并（问题 2）。
4. **循环依赖**：**存在确认循环**（问题 1），按 (a) 抽 SecurityModule 可彻底消除。
5. **不可编译/漏洞**：见 P0 问题 1/3/4/5/7 与 P1 问题 8/10/12/13。
