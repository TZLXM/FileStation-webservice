# v0.2.5 首发验收例外设计

## 目标与范围

为首个正式版本 v0.2.5 提供明确、有审计记录的一次性验收延期，同时保持候选来源、双平台制品摘要、签名密钥配对和受保护环境人工审批。未通过或未执行的验收不得标为通过。后续版本不得自动继承例外。

## 备选方案

- 保持现有门禁：安全边界最严格，但签名候选和首次正式升级验收之间形成循环依赖，无法完成首发。
- 全局跳过验收：会影响后续版本并隐藏风险，不采用。
- 限定 v0.2.5 的结构化首发例外：对明确列出的项目记录延期、原因和风险，仍拒绝失败项，并保留全部制品及签名核验。用户选择此方案。

## 约束

- 仅对版本 v0.2.5 和明确列出的验收字段允许结构化延期；不得将任意 pending 或 failed 当作通过。允许延期的完整字段列表须以用户对首发范围的确认及具体证据审查为准。
- 已授权的范围包括 Linux 实机 bootstrap、两平台真实更新和提交前回滚；其他字段仍须通过，除非用户明确批准延期。例外记录须逐项写明原因、风险、批准依据和关闭条件，记录候选完整 SHA、run ID 与双平台摘要；未知字段、缺少记录或两份候选数据不一致均拒绝。两份数据同时更改时，一致性检查本身不能验证批准引用：审批人须核对批准记录与候选身份，变更候选后重新批准。
- 精确匹配版本及 tag，不使用版本范围或通配符；已发布版本不得通过移动 tag、覆盖制品或删除重建来重复使用例外。发布失败后重试须使用同一已批准候选，候选变化须重新批准。
- 候选 source commit、成功 run、双平台 digest、候选 provenance 与重建字节核验不可省略；真实私钥留在受保护的 release-signing 环境，签名前校验固定公钥配对，维持 v* 标签及人工审批规则。
- 真实更新、回滚与 Linux 实机验收未通过时必须如实标注；不能用夹具、不同候选或合成结果充当实机证据。记录风险和后续关闭条件，公开发布说明应准确披露。
- 确保未来版本不会沿用首发例外，适用范围有针对性的负向测试；发布后可移除例外。不得为了通过而绕过或删除其他安全检查。
- 先提交并审阅规则改动，再以准确的候选提交产生 CI/RC；按照现有源码与证据提交差异限制绑定原始制品与验收证据，推送版本标签，等待 protected environment 审批及发布结果。保留用户工作区中的未提交修改。

## 验证

对例外正负边界、失败状态、其他版本、缺失来源或摘要运行针对性测试；完成仓库规定的测试、typecheck、build 和 diff 检查，并对冻结输入进行独立审阅。正式发布状态以 GitHub workflow 和 Release 实际结果为准。
