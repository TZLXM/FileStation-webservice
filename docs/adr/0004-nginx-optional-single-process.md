# ADR-0004: Nginx 改为可选组件，支持单进程静态托管模式

## 状态
accepted

## 上下文

初始设计（设计文档 v2.2）将 Nginx 作为部署的必需组件：Node.js 只绑定 `127.0.0.1`，前端静态文件由 Nginx 托管，`/api` 反代到后端，初始化端点 `/api/v1/auth/init` 由 Nginx `allow/deny` 限制仅本机可达。

但实际使用场景包含**局域网直连**（无公网暴露、无域名、无 TLS 需求），强制 Nginx 带来不必要的部署复杂度：

1. 用户需要额外安装、配置、维护一个 Web 服务器
2. Windows 桌面环境（项目主要目标平台之一）Nginx 运维成本高
3. 初始化端点的本机限制本质是防"公网场景下远程抢先初始化"——局域网直连场景此威胁不存在，且初始化 Token 本身已是哈希存储、一次性、10 分钟过期的强保护

同时，原实现对 Nginx 存在隐性硬耦合：监听地址写死 `127.0.0.1`、CORS 只放行 vite 开发端口、后端无静态托管能力——即"不使用 Nginx"实际上无法工作，与设计意图（Nginx 是推荐项而非必选项）矛盾。

## 决策

引入三种明确的部署模式，由启动脚本和环境变量选择：

1. **单进程模式（默认，`npm start`）**：设置 `FILESTATION_SERVE_STATIC=true` + `FILESTATION_HOST=0.0.0.0`，后端通过 `@nestjs/serve-static` 托管 `apps/web/dist`，SPA 路由回退 index.html（`exclude: /api/*`），静态资源与 API 同端口同域。CORS 自动关闭（同源无跨域）。
2. **Nginx 反代模式（`npm run start:bynginx`）**：`FILESTATION_HOST=127.0.0.1`，不托管前端，行为与原设计一致。公网（FRP）部署推荐此模式。
3. **开发模式（`npm run dev`）**：vite 开发服务器 + 后端分离，CORS 放行 5173。

配套约定：

- 静态产物路径基于模块位置（`__dirname`）解析，与启动目录无关
- `FILESTATION_CORS_ORIGINS` 可显式覆盖 CORS 白名单
- 启动日志明确打印当前部署模式，避免"以为有静态托管实际没有"的混淆

## 后果

**正面：**

- 局域网/单机部署零依赖：`npm run build && npm start` 即可用
- Nginx 从"隐性必需"变为"显式可选"，与设计意图一致
- 同域部署消除一类 CORS 问题

**负面：**

- 无 Nginx 的公网部署失去初始化端点的网络层本机限制，仅剩 Token 保护（缓解：Token 哈希存储、一次性、10 分钟过期；文档明确建议公网用 Nginx 模式）
- Node.js 直接承担静态文件服务负载（对单管理员私有站可忽略）
- 单进程模式默认监听 `0.0.0.0`，误在公网机器上启动会直接暴露（缓解：文档警示 + 生产环境强制 JWT_SECRET）

## 替代方案

1. **保持 Nginx 必需**——拒绝：与用户的局域网直连场景冲突，部署复杂度不成比例
2. **Express 中间件手写静态托管（不引入 @nestjs/serve-static）**——拒绝：SPA 回退、MIME、缓存头等需自行处理，重复造轮子
3. **前端产物打包进后端二进制（如 pkg/sea）**——拒绝：构建链复杂化，当前 monorepo 结构下收益小
