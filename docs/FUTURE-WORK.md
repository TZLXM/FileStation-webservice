# Future Work

## 按推送类型区分普通提交与版本发布

状态：待设计和实施；本条不改变现有工作流。

- 普通分支提交及文档修改推送到 GitHub 时，不自动触发耗时的发布构建。
- 将版本标签（例如 `v0.2.5`）推送到 GitHub 时，以标签指向的准确提交为输入，进入 CI、双平台候选制品构建与发布流程。
- 发布顺序必须保留版本与源码一致性验证、CI、候选制品 provenance 与 digest 核验、真实验收、受保护 `release-signing` 环境人工审批及失败即停止；不可因标签推送绕过签名或验收。
- 设计时先核对现有 `release.yml` 的 `v*` tag 触发、candidate 精确源码及 evidence/promotion 约束，避免标签触发循环、重复构建、旧制品误用或无意发布。
- 明确 CI 是否保留手动运行、分支保护所需检查如何适配，以及普通推送不自动运行时由谁负责在合并前验证。
- 本需求属于后续工作，不影响当前 `6378ea7` 的候选验证；未授权在本轮实施工作流变更或推送版本标签。
