# Future Work

## 首次发布后的签名更新与回滚验收

状态：待设计和实施；本条不改变现有发布门或声明验收通过。

- 首次正式发布后，准备符合版本规则的更高版本，使用正式信任根和实际发布渠道验证 Windows 托管安装的签名检查、下载、更新、独立重启与数据完整性。
- 在隔离环境验证提交前受控故障后的回滚、旧版本恢复及数据库和存储完整性；单独记录 Linux 实机验收延期与结果。
- 设计受保护的签名候选及验收路径，解决现有候选无签名、正式签名前要求更新验收的循环依赖；不得泄露私钥或把测试产物冒充正式发布证据。
- 首次发布前核对并补齐 375px、TOTP/恢复码、刷新续传、Docker 和 Nginx 等尚未完成或尚未绑定最终候选的证据；这些项目不属于已批准的延期范围。不能把 pending 填成 passed。

## 按推送类型区分普通提交与版本发布

状态：待设计和实施；本条不改变现有工作流。

- 普通分支提交及文档修改推送到 GitHub 时，不自动触发耗时的发布构建。
- 将版本标签（例如 `v0.2.5`）推送到 GitHub 时，以标签指向的准确提交为输入，进入 CI、双平台候选制品构建与发布流程。
- 发布顺序必须保留版本与源码一致性验证、CI、候选制品 provenance 与 digest 核验、真实验收、受保护 `release-signing` 环境人工审批及失败即停止；不可因标签推送绕过签名或验收。
- 设计时先核对现有 `release.yml` 的 `v*` tag 触发、candidate 精确源码及 evidence/promotion 约束，避免标签触发循环、重复构建、旧制品误用或无意发布。
- 明确 CI 是否保留手动运行、分支保护所需检查如何适配，以及普通推送不自动运行时由谁负责在合并前验证。
- 本需求属于后续工作；当前首发例外不实施按推送类型区分工作流的调整。
